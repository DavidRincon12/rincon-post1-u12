# ADR-001: Capas simples para la persistencia; el punto de extensión de notificación ya cubre el próximo cambio conocido

## Estado: Aceptado — 2026-11-20

## Contexto

Con Chain of Responsibility (validación), Strategy (cálculo) y Observer (notificación) ya integrados, hay que decidir si el sistema migra a arquitectura Hexagonal completa, con puertos e interfaces intermedias para todas sus dependencias externas, o si se mantiene en capas simples.

El criterio de la Guía (sección 6.2) es que Hexagonal vale la pena "en sistemas que sobrevivirán 3 años o más con cambios de infraestructura". Hay que evaluarlo por separado para cada dependencia externa, con datos de este proyecto:

- **Persistencia.** Hay una sola entidad (`SolicitudReembolso`), un solo repositorio (`RepositorioSolicitudesJpa`) con un único método derivado (`findByEmpleadoIdAndEstado`) y un solo consumidor (`SolicitudReembolsoService`). No existe ningún plan de cambiar de motor de base de datos: H2 hoy y, en producción, cualquier motor relacional que JPA soporte sin cambiar código. El cambio de infraestructura que exigiría el criterio no está anunciado.
- **Notificación.** Contabilidad sí anunció para el próximo trimestre la integración con un sistema externo de pagos por API para las solicitudes aprobadas. Es un cambio de infraestructura con fecha. Hoy `SolicitudReembolsoService` depende solo de `List<ObservadorCambioEstado>`, no de los notificadores concretos.

## Decisión

1. **Persistencia: se mantienen capas simples.** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin una interfaz de puerto `RepositorioSolicitudes` ni un adaptador JPA. Un puerto hoy sería una abstracción especulativa (YAGNI): una interfaz con una sola implementación y ningún caso de uso que pida una segunda. El dominio igual queda libre de JPA, porque el mapeo vive en `META-INF/orm.xml`.
2. **Notificación: no se introduce ningún cambio.** `ObservadorCambioEstado` ya es el punto de extensión necesario. El próximo trimestre, `NotificadorContabilidad` reemplazará su implementación interna (hoy un log) por la llamada al cliente HTTP de la API de Contabilidad, sin modificar `SolicitudReembolsoService` ni los otros observadores. Ese cliente HTTP vivirá en `infraestructura`; para que `procesamiento` no dependa de `infraestructura` (Regla 1 de ArchUnit), el observador recibirá una interfaz propia del cliente definida en `procesamiento.notificacion`, que en ese momento sí tendrá un motivo real: un sistema externo.

## Alternativas consideradas

| Alternativa | Pros | Contras | Costo de revertir |
|---|---|---|---|
| Hexagonal completa (puertos para persistencia y notificación) | Simetría; se podría cambiar de motor sin tocar el servicio | Interfaces y mappers sin un segundo adaptador real; más archivos que leer para una sola entidad | Alto: quitar puertos toca servicio, pruebas y configuración |
| **Capas simples en persistencia + Observer como seam de notificación (elegida)** | Cero abstracciones especulativas; el único cambio con fecha ya tiene su punto de extensión | Asimetría que hay que explicar (este ADR) | Bajo: extraer la interfaz de puerto desde `RepositorioSolicitudesJpa` es mecánico, con un solo consumidor |
| Puerto solo para persistencia | Prepara un cambio de motor | Prepara el cambio que no está anunciado e ignora el que sí | Medio |

## Consecuencias

Positivas:
- No se agregan interfaces ni mappers de persistencia sin un caso de uso real que los justifique.
- La integración de Contabilidad, el único cambio de infraestructura con fecha conocida, ya tiene su punto de extensión listo.
- Las reglas ArchUnit verifican los límites que sí existen; ninguna asume un puerto de persistencia.

Negativas:
- Si en el futuro hace falta cambiar de motor de base de datos o de tecnología de persistencia (por ejemplo, un servicio externo de documentos), el puerto deberá introducirse en ese momento. Se acepta esa deuda técnica de forma consciente.
- Un revisor que espere simetría total (puertos en todas las dependencias externas) puede leer la asimetría como inconsistencia si no lee este ADR.
- Los observadores se ejecutan en el mismo hilo de la petición: cuando `NotificadorContabilidad` llame a una API externa, una caída de esa API afectaría la respuesta de `PUT /estado`. Se resolverá con timeout y manejo de errores en ese observador cuando llegue la integración.

## Cuándo revisar

- Se sostiene con (hoy): una entidad, un repositorio, un consumidor, sin plan de migración de base de datos.
- Revisar si: se anuncia un cambio de motor o de tecnología de persistencia, aparece un segundo consumidor de la persistencia (por ejemplo, un proceso por lotes) o se necesita probar el servicio sin Spring Data.
